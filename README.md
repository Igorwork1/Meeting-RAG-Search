# Meeting-RAG-Search

**Тема курсового проекта:** Разработка сервиса автоматической транскрибации и семантического поиска по записям встреч на основе RAG-архитектуры

**Образовательная программа:** Искусственный интеллект в маркетинге и управлении продуктом  
**Формат проекта:** курсовой проект, 1 курс  
**Назначение:** внутренний сервис для команды стартапа MetaPromt
---

# О проекте
Сервис предназначен для автоматической обработки записей онлайн-встреч команды MetaPromt. Он позволяет загружать аудиофайлы встреч, получать текстовую расшифровку, сохранять результаты обработки в базе данных и задавать вопросы по содержанию встреч в формате чат-бота.

Проект построен на RAG-архитектуре: пользовательский вопрос преобразуется в embedding-вектор, после чего система ищет релевантные фрагменты транскриптов в PostgreSQL с расширением pgvector и передаёт найденный контекст в языковую модель для формирования ответа.

---

# Проблема

В рамках деятельности команды MetaPromt регулярно проводятся онлайн-встречи, в которых участвуют руководитель проекта, разработчики, SEO-специалисты и сотрудники различных направлений. Совещания проходят в сервисе Bitrix24.

На встречах обсуждаются:
- текущие задачи
- результаты работы
- возникающие проблемы
- планы и дальнейшие действия

Для того чтобы сохранить содержание встречи, используется следующий процесс.
1. Во время совещания ответственный сотрудник записывает аудио встречи.
2. После окончания встречи аудиофайл выгружается вручную.
3. Файл отправляется в сторонний сервис транскрибации.
4. Полученный текст передается в нейросетевой сервис для суммаризации.
5. Итоговое резюме встречи отправляется в рабочий чат команды.

Параллельно Bitrix24 также записывает встречу и спустя некоторое время отправляет автоматический отчёт по совещанию.

Несмотря на наличие частичной автоматизации, текущий процесс имеет ряд проблем.
- процесс включает несколько отдельных сервисов;
- значительная часть операций выполняется вручную;
- результаты обработки встреч отправляются в чат в виде ссылок;
- отсутствует централизованное хранилище знаний;
- со временем формируется большое количество документов и текстовых файлов;
- поиск нужной информации требует просмотра переписки или ручного поиска по документам.

В результате сотрудники вынуждены тратить дополнительное время на:

- поиск нужной информации в переписке;
- просмотр записей встреч;
- анализ текстовых протоколов.

Таким образом, в текущем процессе отсутствует единая система, которая позволяла бы автоматически транскрибировать встречи, структурировать информацию и выполнять быстрый семантический поиск по их содержанию.

Важно, что разрабатываемый сервис не заменяет Bitrix24 полностью. Bitrix24 продолжает использоваться для проведения встреч и хранения исходных записей. Новый сервис решает другую задачу: он создаёт удобный слой для транскрибации, хранения текстовых данных и поиска информации по содержанию встреч.

---

# Решение

Разрабатываемый сервис решает эту проблему за счёт:

- автоматической транскрибации аудио
- централизованного хранения протоколов
- семантического поиска по содержанию
- генерации ответов на основе контекста встречи

Пользователь может задать вопрос:

"Какие задачи были назначены на встрече?"

и получить ответ, сформированный на основе содержания обсуждения.

# Основные возможности

Сервис предоставляет следующий функционал:

- загрузка аудиофайлов встреч в формате MP3/WAV;
- автоматическая транскрибация аудио;
- формирование краткой суммаризации встречи;
- сохранение транскриптов, summary и чанков в PostgreSQL;
- генерация embedding-векторов для текстовых фрагментов;
- семантический поиск по базе встреч;
- формирование ответа на вопрос пользователя на основе найденных фрагментов;
- хранение истории вопросов и ответов.

Сервис не хранит исходные аудиофайлы после обработки. Записи встреч остаются в Bitrix24, а в базе сервиса сохраняются только текстовые данные и их векторные представления.

# Архитектура системы

Сервис реализован по клиент-серверной архитектуре. Pipeline обработки данных:

1. пользователь загружает аудио
2. система выполняет транскрибацию через ASR-модель GigaAM-v3
3. выполняется резюмирование текста с помощью LLM и сохраняется в базе данных
4. генерируются embeddings
5. embedding-векторы сохраняются в PostgreSQL с расширением pgvector
6. пользователь задаёт вопрос
7. выполняется семантический поиск
8. найденный контекст передаётся в LLM
9. генерируется ответ

# Структура базы данных

В проекте используется PostgreSQL с расширением pgvector. Основные таблицы:

- `cyberecho_meetings` — хранит информацию о встрече: название, дату, описание, участников и summary;
- `cyberecho_meeting_chunks` — хранит текстовые фрагменты транскрипта и их embedding-векторы;
- `cyberecho_meeting_asks` — хранит вопросы пользователей и ответы RAG-системы.

Связь между встречами и чанками реализована через поле `meeting_id`. Такой подход позволяет хранить не только общий протокол встречи, но и отдельные смысловые фрагменты, по которым выполняется семантический поиск.

# Запуск проекта

## Подготовка (один раз)

1. Клонировать репозиторий и перейти в папку проекта.
2. Создать и активировать виртуальное окружение:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

3. Создать файл `.env` в корне проекта (можно скопировать из примера у команды). Минимум нужны:
   - `POSTGRES_CONNECTION_STRING` — подключение к PostgreSQL
   - `RUVDS_DE_LITELLM_BASE_URL`, `RUVDS_DE_LITELLM_MODEL`, `RUVDS_DE_LITELLM_METAPROMT_BULLET_KEY` — основной LLM (LiteLLM)
   - `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`, `YANDEX_MODEL` — fallback на прямой YandexGPT, если LiteLLM недоступен
   - `API_URL=http://127.0.0.1:8000` — адрес бэкенда
   - `GIGA_EMBEDDING_MODEL`, `TRANSCRIBE_CHUNK_SECONDS` — по желанию

4. Установить **ffmpeg** и добавить в PATH (нужен для нарезки аудио).

5. Проверить БД:

```powershell
python -c "from services.db import check_db_connection; print(check_db_connection())"
```

Должно быть `ok: True`, а в базе должны быть таблицы `cyberecho_meetings`, `cyberecho_meeting_chunks` и `cyberecho_meeting_asks`.

## Backend (FastAPI)

Запускается в **отдельном терминале** из корня проекта:

```powershell
.\.venv\Scripts\Activate.ps1
uvicorn services.main:app --host 127.0.0.1 --port 8000
```

Проверка:
- `http://127.0.0.1:8000/health` → `{"status":"ok"}`
- `http://127.0.0.1:8000/docs` — Swagger UI

Основные ручки:
- `POST /api/meetings/process` — загрузка аудио (обработка в фоне)
- `GET /api/meetings/jobs/{job_id}` — статус фоновой задачи
- `POST /api/chat/ask` — RAG-чат

## Frontend (Streamlit)

Запускается во **втором терминале**:

```powershell
.\.venv\Scripts\Activate.ps1
streamlit run views/streamlit_app.py
```

Откроется браузер (обычно `http://localhost:8501`).

Страницы:
- **Download Page** — загрузка mp3/wav, метаданные, запуск обработки в фоне
- **Chat Bot** — вопросы по сохранённым встречам (можно открыть, пока идёт обработка файла)
- **About Service** — описание сервиса

> **Важно:** сначала поднять backend (`uvicorn`), затем Streamlit. Без бэкенда загрузка аудио не работает.

# RAG-подход

RAG-подсистема используется для поиска релевантных фрагментов транскриптов и формирования ответа на вопрос пользователя.

Обработка происходит следующим образом:

1. транскрипт встречи очищается и разбивается на смысловые фрагменты;
2. для каждого фрагмента создаётся embedding-вектор размерностью 2048;
3. чанки и векторы сохраняются в PostgreSQL;
4. вопрос пользователя также преобразуется в embedding-вектор;
5. в базе выполняется поиск ближайших фрагментов по косинусному расстоянию;
6. Top-3 найденных чанка передаются в LLM как контекст;
7. языковая модель формирует итоговый ответ.

Для расчёта близости используется оператор pgvector `<=>`. Чем меньше cosine distance, тем ближе фрагмент по смыслу к пользовательскому запросу.

# Тестирование

## Нагрузочное тестирование (Locust)

Сценарии в `tests/locustfile.py`. **Сначала запустите backend** (`uvicorn`), затем Locust — в **третьем терминале** из корня проекта:

```powershell
.\.venv\Scripts\Activate.ps1
pip install locust
locust -f tests/locustfile.py --host http://127.0.0.1:8000
```

Откроется веб-интерфейс: [http://localhost:8089](http://localhost:8089). Укажите число пользователей (Users) и скорость разгона (Spawn rate), нажмите **Start swarming**.

Альтернатива без UI (headless):

```powershell
locust -f tests/locustfile.py --host http://127.0.0.1:8000 --headless -u 10 -r 2 -t 60s
```

- `-u 10` — 10 виртуальных пользователей  
- `-r 2` — по 2 пользователя в секунду при старте  
- `-t 60s` — длительность теста  

По умолчанию Locust нагружает «лёгкие» ручки: `/health`, `/db/health`, `POST /api/chat/ask`, опрос статуса jobs.

**Тяжёлые сценарии** (транскрибация и полный пайплайн встречи) — только при явном включении:

```powershell
$env:LOCUST_HEAVY="1"
$env:LOCUST_AUDIO_PATH="C:\path\to\sample.mp3"
locust -f tests/locustfile.py --host http://127.0.0.1:8000
```

Без `LOCUST_AUDIO_PATH` для тяжёлых тестов подставляется короткий синтетический WAV.

Тот же запуск через Python-модуль (если команда `locust` не в PATH):

```powershell
python -m locust -f tests/locustfile.py --host http://127.0.0.1:8000
```
